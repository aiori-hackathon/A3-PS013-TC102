# TraceForge
### Evidence-Centric Incident Investigation Platform for Small Cybersecurity Teams

**AIORI-3 Hackathon | Problem Statement PS-013**

> Collect evidence. Normalize events. Reconstruct timelines. Trace findings back to their supporting records.

---

## 1. Project Overview

TraceForge is an evidence-centric incident investigation platform designed to help small cybersecurity teams collect, organize, and analyse digital evidence from different log sources.

During a cybersecurity incident, investigators often need to examine multiple log files generated by different systems. These files may contain authentication records, web access information, operating system events, and other security-related activities. Reviewing them individually can make it difficult to understand the sequence of events and identify relationships between suspicious activities.

TraceForge aims to simplify this process by providing a unified workflow for evidence collection, integrity verification, log parsing, event normalization, chronological timeline reconstruction, and explainable rule-based analysis.

The platform connects original evidence files with their parsed events and generated findings, helping investigators understand not only what activity was detected but also which records support that finding.

**Project Status:** Working prototype with core investigation features implemented and additional capabilities planned for future development.

---

## 2. Problem Statement

**PS-013 — Incident Timeline and Evidence Collection for Small Teams**

Small cybersecurity teams may not have access to complex enterprise security platforms or dedicated forensic infrastructure. Investigating incidents manually across multiple log files can be time-consuming and make it difficult to maintain a clear relationship between original evidence and identified suspicious activities.

Common challenges include:

- Collecting evidence from different log sources.
- Working with multiple log formats and timestamp representations.
- Maintaining the integrity of collected evidence.
- Reconstructing the chronological sequence of events.
- Identifying suspicious patterns across log records.
- Connecting investigation findings to their original supporting records.
- Preparing structured investigation reports.

TraceForge addresses these challenges through a structured evidence-to-investigation workflow.

---

## 3. Proposed Solution

TraceForge provides a web-based platform where investigators can create investigations, upload supported evidence files, verify file integrity, parse log records into structured events, and review those events through a chronological timeline.

The platform also applies explainable detection rules to identify selected suspicious activity patterns. Each generated finding includes its reasoning and links to the relevant event records, allowing investigators to review the evidence behind the result.

The proposed workflow is:

1. Create an investigation.
2. Upload digital evidence files.
3. Validate uploaded files and calculate SHA-256 hashes.
4. Parse supported log formats.
5. Convert recognizable records into structured events.
6. Review events through a chronological timeline.
7. Analyse selected suspicious patterns using detection rules.
8. Review findings and their supporting event records.
9. Generate reports and export investigation-related data.

---

## 4. Innovation & Key Differentiators

The central idea behind TraceForge is not simply to display log files or generate alerts. It is to maintain a traceable relationship between collected digital evidence, normalized security events, reconstructed timelines, and investigation findings.

### 4.1 Evidence-to-Finding Traceability

A major focus of TraceForge is connecting every generated finding to the event records that support it.

Instead of presenting a suspicious activity alert without context, the platform stores linked event references and provides the finding's rule identifier, severity, rationale, and relevant activity details.

This helps investigators move from a finding back to the records that contributed to it.

### 4.2 Evidence Integrity at Intake

TraceForge calculates a SHA-256 hash when evidence is uploaded and stores the hash with the evidence metadata.

The platform also supports integrity verification by comparing the current file hash with the stored hash. This helps identify whether the stored evidence content has changed after intake.

### 4.3 Multiple Log Sources Through Structured Parsing

Different systems produce logs in different formats. TraceForge supports selected Linux authentication logs, Apache/Nginx-style web access logs, Windows Event Viewer CSV exports, and JSON-based records.

Recognizable records are converted into a common event structure so that investigators can review different sources through a consistent timeline.

### 4.4 Explainable Rule-Based Detection

The current detection approach uses deterministic rules rather than presenting unexplained automated predictions.

Findings include the matching rule, severity, rationale, related event records, and a recommended review action. This makes the detection process easier to inspect and validate.

### 4.5 Transparent Parsing Gaps

Not every log record contains complete or recognizable information. TraceForge aims to preserve the distinction between successfully parsed records and records that could not be fully interpreted.

Missing or unrecognized timestamps are not treated as confirmed chronological information. This is important because an investigation should not create certainty where the original evidence does not provide it.

### 4.6 A Foundation for Cross-Source Investigation

The current version establishes the foundation for structured event analysis. Future development will expand this approach to correlate activity across multiple evidence files and provide a broader incident-level view.

## 5. Implemented Features

The following features are included in the current working prototype.

### Investigation Management
- User registration and login.
- Create and manage investigations.
- User-specific access restrictions.
- Investigation history and audit records.

### Evidence Collection
- Upload supported `.log`, `.txt`, `.csv`, and `.json` files.
- Validate file types and upload sizes.
- Store evidence using randomized storage filenames.
- Preserve original filename and file-size metadata.
- Calculate SHA-256 hashes at intake.
- Detect duplicate file content using hashes.
- Verify evidence integrity against the stored hash.

### Log Parsing and Event Normalization
- Parse selected Linux authentication-style logs.
- Parse Apache/Nginx-style web access logs.
- Parse Windows Event Viewer CSV exports.
- Parse JSON arrays, objects, and JSONL records.
- Extract recognizable timestamps, event types, source IP addresses, usernames, severity information, and original messages where available.
- Retain source line information where available.
- Normalize recognizable timestamps to UTC.
- Provide information about parsing gaps.

### Timeline and Investigation Analysis
- Review parsed events chronologically.
- Search parsed events.
- Filter events by severity.
- Use pagination for event review.
- Identify selected suspicious activity patterns through deterministic rules.
- Link findings to their supporting persisted event records.

### Current Detection Rules

| Rule ID | Detection | Purpose |
|---|---|---|
| AUTH-001 | Repeated authentication failures | Identifies repeated authentication failures from the same source IP. |
| AUTH-002 | Successful login after repeated failures | Identifies a successful login following a recent repeated-failure cluster. |
| WEB-001 | Repeated HTTP error responses | Identifies repeated HTTP 401, 403, or 404 responses from the same source. |
| SYS-001 | Repeated system warning/error messages | Identifies repeated common warning or error messages. |

Detection rules provide investigation leads, not proof of compromise. The AUTH-002 correlation uses a 15-minute window when usable timestamps are available. Undated records cannot establish temporal confirmation.

### Reports and Exports
- Generate PDF reports.
- Export structured data in JSON.
- Export events in CSV format.
- Export findings in CSV format.
- Export evidence metadata in CSV format.
- Generate a ZIP package for a selected evidence record with a package manifest.
- Maintain report and investigation history.

### Security and Data Handling
- Password hashing using PBKDF2-HMAC-SHA256 with individual salts.
- Signed, expiring bearer tokens.
- Account ownership checks and user-specific access restrictions.
- Upload validation and randomized storage filenames.
- Security response headers.
- No-store API responses.
- CSV formula-injection mitigation.
- Audited original-evidence downloads.

## 7. Future Development Roadmap

TraceForge is designed with a broader vision of becoming a unified evidence-centric investigation platform. The following capabilities are planned for future development and are not claimed as completed features in the current prototype.

### 7.1 Multi-File Evidence Collection

The future version aims to support uploading multiple evidence files within a single investigation.

Investigators will be able to collect logs from different sources, such as authentication systems, web servers, and operating system event exports, under one investigation.

This will provide a more realistic workflow for incidents involving multiple systems and reduce the need to analyse every file as an isolated investigation.

### 7.2 Evidence Grouping and Reusable Workspaces

A planned evidence grouping feature will allow investigators to organize related files into logical collections.

For example, files collected from a particular server, time period, or suspected incident could be placed in a common group.

Reusable workspaces will help investigators revisit related evidence and continue analysis without repeatedly setting up separate investigations.

### 7.3 Advanced Duplicate and Similarity Detection

Future development will explore two complementary approaches:

- **Exact duplicate detection:** Identify files with identical content using cryptographic hashes.
- **Similarity analysis:** Explore techniques to identify files containing overlapping or similar records, even when their complete contents are different.

This could reduce repeated analysis and help investigators identify related evidence. Similarity results will be treated as investigative suggestions, not proof of identical content.

### 7.4 Individual and Group-Level Dashboards

The planned dashboard architecture will provide two levels of investigation visibility.

**Individual Evidence Dashboard**
- Evidence metadata.
- Integrity verification status.
- Parsed events.
- Related findings.
- File-level analysis information.

**Group-Level Dashboard**
- Overview of multiple related evidence files.
- Combined event information.
- Findings across the evidence group.
- Investigation-level activity summaries.

This will help investigators move between individual file analysis and a broader incident-level view.

### 7.5 Modular Parser Registry and Advanced Normalization

TraceForge aims to develop a more flexible parser architecture where additional log formats can be supported through independent parser modules.

A common event schema will help standardize information such as timestamps, usernames, IP addresses, event types, and original messages.

Further improvements may include:
- Additional log format support.
- Better timezone handling.
- Clock-skew awareness.
- More detailed parsing metadata.
- Improved preservation of original record context.

### 7.6 Cross-Source Event Correlation

One of the major planned improvements is correlating events across multiple evidence files.

For example, repeated authentication failures in one log file could be examined alongside a successful login recorded by another source.

Instead of analysing each file separately, the platform will aim to identify relationships between events from different systems and help reconstruct a more complete incident timeline.

### 7.7 Enhanced Evidence Integrity and Verification

The current implementation uses SHA-256. Future work may explore additional hashing algorithms, including SHA3-256, along with stronger evidence-management workflows.

Potential improvements include:
- More detailed evidence handling history.
- Expanded integrity verification records.
- Stronger chain-of-custody documentation.
- Verification information included in investigation exports.

These improvements aim to strengthen traceability. They will not, by themselves, establish forensic certification or prove the authenticity of evidence before intake.

### 7.8 Advanced Detection and Anomaly Analysis

The current version uses deterministic rule-based detection. Future development may explore additional techniques to identify activity that does not match predefined patterns.

Potential directions include:

**Anomaly Detection**

Investigate methods such as Isolation Forest to identify unusual event patterns that may require further review.

**AI-Assisted Explanations**

Explore local language models, including Ollama-supported models, to help explain detected activity in simpler investigative language.

**Combined Analysis**

Compare rule-based findings with anomaly-based results to provide investigators with additional context.

These techniques will be treated as optional investigative aids. Their results will require human review and will not automatically establish that a security incident has occurred.

### 7.9 Comprehensive Investigation Export

The current prototype supports exports related to individual evidence records. Future development aims to provide a consolidated export for an entire investigation containing multiple evidence files.

A planned investigation package may include:
- Investigation summary and generated report.
- Original uploaded evidence files.
- Evidence metadata and integrity hashes.
- Parsed event records.
- Related findings.
- Export manifest describing the package contents.

This will make investigation results easier to share, retain, and review outside the platform.

### 7.10 Synthetic Incident Scenarios and Evaluation

TraceForge plans to use controlled synthetic incident scenarios to evaluate its investigation workflow.

Potential scenarios include:
- Repeated login failures.
- Successful login following suspicious authentication activity.
- Unusual web access patterns.
- Repeated system warnings or errors.

The evaluation will compare expected activity with the platform's parsing and detection results.

Planned evaluation areas:
- Correct parsing of supported records.
- Accuracy of chronological event ordering.
- Detection of intended rule-based patterns.
- Traceability of findings to original supporting records.
- Identification and documentation of parsing gaps.
- Comparison with manual investigation.

Performance and accuracy claims will only be made after testing and measurement.

## 8. Limitations of the Current Prototype

The current version is a working academic prototype. The following limitations are important:

- Native Windows `.evtx` parsing is not implemented; the current parser supports Windows Event Viewer CSV exports.
- Live endpoint monitoring and remote evidence collection are not implemented.
- Malware scanning is not included.
- AI-based prediction and anomaly detection are not currently implemented.
- Threat intelligence integrations are not included.
- Advanced timezone and clock-skew correction are not fully implemented.
- Cross-source correlation across multiple evidence files is planned, not yet implemented.
- The consolidated ZIP export is currently associated with a selected evidence record rather than a complete multi-file investigation.
- The current prototype uses SQLite and local file storage.
- The platform does not claim certified forensic chain-of-custody compliance.

TraceForge is intended to assist investigation workflows. Its findings should be reviewed by a human investigator and should not be treated as conclusive proof of malicious activity.

## 9. Installation and Setup

### Prerequisites

- Python 3.10 or a compatible version supported by the project dependencies.
- Git.
- A web browser.

### Step 1: Clone the Repository

```bash
git clone https://github.com/aiori-hackathon/A3-PS013-TC102.git
cd A3-PS013-TC102
```

### Step 2: Create a Virtual Environment

**Windows:**

```bash
python -m venv .venv
.venv\Scripts\activate
```

### Step 3: Install Dependencies

```bash
pip install -r requirements.txt
```

### Step 4: Configure Environment Variables

Create your local `.env` file using `.env.example` as the reference.

Keep local secrets and environment-specific configuration out of Git. Do not upload your actual `.env` file.

### Step 5: Run the Application

On Windows, the repository includes a startup script:

```bash
run_windows.bat
```

Alternatively, use the application entry point and startup command documented in the project deployment guide.

Open the local address printed by the application in your browser.

## 15. Long-Term Vision

The long-term vision of TraceForge is to bring evidence collection, evidence organization, integrity verification, event normalization, cross-source correlation, timeline reconstruction, and explainable analysis into one unified investigation workflow.
